# Room Reservation API

A REST API developed in Java with Spring Boot to manage meeting room reservations and calculate daily occupancy statistics. This API saves data in in-memory data structures and safely handles concurrent access.

## Technologies & Versions

- **Java:** `21`
- **Framework:** Spring Boot
- **Dependency Manager:** Maven

## How to run the application

1. Clone this repository to your local machine.
2. Open the terminal in the project's root directory.
3. Execute the following command using the Maven Wrapper already included in the project:

   **Linux/macOS:**

   Bash
```

./mvnw spring-boot:run

```

**Windows:**

DOS
```

mvnw.cmd spring-boot:run

```

4. The application will be available at `http://localhost:8080`.

## How to run the automated tests

To run the unit test suite and verify the business rule validations, execute the following command in the terminal (at the project root):

## Architecture Decisions & Trade-Offs

1. **Safe and Read-Optimized Storage:** To handle concurrent data access, a `ConcurrentHashMap<LocalDate, List<Reserva>>` was implemented to store days using `LocalDate`, and the schedule through `List<Reserva> x = CopyOnWriteArrayList<>()`. The `ConcurrentHashMap` structure was chosen because its `compute()` method allows a write-lock on a specific bucket (day), preventing double bookings. The `CopyOnWriteArrayList` was chosen for the schedules because it is read-heavy, making it fast for data retrieval, since checking is the most frequent action in a reservation system. This partition by date makes statistics querying O(1) to locate the day and O(n) to iterate through that day's reservations, avoiding a full collection scan.
2. **Timezone Shielding:** `OffsetDateTime` was chosen instead of `LocalDateTime` to preserve the client's original offset. The `@JsonFormat(without = JsonFormat.Feature.ADJUST_DATES_TO_CONTEXT_TIME_ZONE)` annotation prevents Jackson from automatically converting the time to the server's timezone, ensuring that 14:00-03:00 is stored and returned exactly as it was sent.
3. **Pragmatic Modeling:** Since there is no database usage, I opted to use classes like `Reserva` and `Estatistica` as both Models and DTOs, given that their functions are simple and they are utilized by the controller, service, and repository.
4. **Global Exception Handling:** To meet the requirement for useful and consistent error messages, a global ErrorHandler (`TratadorDeErros`) was implemented. It intercepts exceptions thrown by the system before they are sent to the client, clarifies the error, and generates a description based on its origin. It catches exceptions thrown by both the system's own objects and by Jackson during input parsing.
5. **Strict API Contract:** To enforce a strict API contract, annotations such as `@RequestMapping(produces = MediaType.APPLICATION_JSON_VALUE)` and `@PostMapping(value ="/reservas", consumes = MediaType.APPLICATION_JSON_VALUE)` were used to ensure that any payload entering or leaving the system is strictly formatted as JSON.
